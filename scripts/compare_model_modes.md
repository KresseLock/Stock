# 模型時效性對照實驗（`compare_model_modes.py`）

> 這份文件是給「隔天／幾個月後回來看報告的人」的說明書：**這個實驗在比較什麼、憑什麼判斷結果有效、當初為什麼要做**。
> 程式：[compare_model_modes.py](compare_model_modes.py)　｜　相關結論已收進 [../.claude/CLAUDE.md](../.claude/CLAUDE.md) §4.5 #5、#6。

## 1. TL;DR

| 問題 | 答案 |
| :--- | :--- |
| 這在比什麼？ | 同一段回測區間、同一組風控參數下，**只改變「模型看過多少近期資料」（以及 `--full` 時的因子參數）**，看績效差多少 |

## 2. 為什麼要做這個實驗（起因與兩個誤解）

**起因**：`reports/` 下 2026-04、05、06、07 四份單月回測報表看起來績效不佳，直覺假設是「近一年市場資料沒被訓練進模型，所以預測失敗」。

追查後發現兩個誤解，這也是本實驗的設計動機：

### 誤解一：`BACKTEST_DATE` 決定模型看到多新的資料 ❌

`BACKTEST_DATE` 只決定**資料截斷點**，真正 fit 的訓練集終點由 `train.py` 的日期分位切分決定（`config.TRAIN_SPLIT_RATIO`，預設 0.70），**截斷點的後 30% 會被切給 valid/test，完全不參與 fit**：

| 設定 | 資料截斷 | 實際 fit 訓練集終點 |
| :--- | :--- | :--- |
| `BACKTEST_DATE="20250801"`（生產現值） | 2025-08-01 | **2023-11-27** |
| `BACKTEST_DATE=None` | 2026-08-12 | **2024-08-13** |
| `="20260331"` + 切分 0.95/0.98 | 2026-03-31 | **2025-12-01** |

所以「把 `BACKTEST_DATE` 設成 `None` 就能讓模型吃到最近一年」是錯的 —— 只會把 fit 終點從 2023-11 推到 2024-08。要真的涵蓋近期，必須同時調高切分比例，這就是候選 `b2` / `b2full` 存在的理由。

> `TRAIN_SPLIT_RATIO` / `VALID_SPLIT_RATIO` 是 2026-08-13 為本實驗從 `train.py` 提取到 `config.py` 的（原本寫死 0.7/0.8，違反常數集中原則）。預設值不變，現行行為零影響。

### 誤解二：「每個月都在虧」 ❌

用**同一個現行模型**跑連續區間 2026-04-01~07-31，報酬是 **+37.68%**；而四份單月報表複利起來只有約 **+19.3%**（-1.95% → +22.21% → -1.57% → +1.12%）。

差距來自評估方式本身：本策略 `MIN_HOLD_DAYS` 為 11~23 天、獲利靠肥尾（見 CLAUDE.md §4.5 #1），**按月切割會強制月初空手重建倉、月底截斷未平倉部位**，正好砍在賺錢的地方。且單月賣出紀錄幾乎全是停損（賺錢的部位還沒平倉），只看 `Trade_History` 會誤判成「一直在虧」。

**→ 評估策略一律用連續區間，單月報表只能看交易明細，不能拿來論績效。**

## 3. 這個實驗在比較什麼

四組跑**完全相同的回測區間、資金、風控參數**（含 regime 動態門檻），差異只在模型怎麼來的：

| 代號 | 資料截斷 | 切分比例 | 因子參數 | 特徵矩陣 | 重跑步驟 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `incumbent` | `"20250801"` | 0.70/0.80 | 現行 | 現行 | 無（直接回測現有模型） |
| `b1` | `None` | 0.70/0.80 | 現行 | 現行 | `train` |
| `b2` | 回測起始日前一日 | 0.95/0.98 | 現行 | 現行 | `train` |
| `b2full` | 回測起始日前一日 | 0.95/0.98 | **重新搜尋** | **重新計算** | `optimize`→`feature`→`train` |

- **`b1`／`b2`（預設模式，數分鐘）**：單一變因＝模型 fit 的資料範圍。回答「只重訓模型有沒有用」。
- **`b2full`（`--full`，數小時）**：連 Optuna 貝葉斯因子調參一起重跑。回答「完整重跑 pipeline 有沒有用」。

### 為什麼沒有 `b1full`

`optimize_factors.py` 的防洩漏保護是看 `config.BACKTEST_DATE`：

```python
if cfg_backtest_date is not None and max_data_date > bt_date:
    df_base = df_base[df_base["date"] <= bt_date].copy()   # 截斷保護
```

設 `None` 時**不截斷**，會拿全部資料（含回測區間）去搜尋因子 → 回測區間直接進入優化目標函式 = lookahead。跑出來的數字必然虛高、不可採信。**完整重訓對照只能用「截斷於回測起始日前一日」的設定。**

## 4. 如何判斷結果有效

### 4.1 採用判準：雙贏制

報告第三節會自動判定，判準與 CLAUDE.md §4.5 #4 的方法論一致：

| 情況 | 判定 |
| :--- | :--- |
| 報酬↑ 且 MDD 不變差 | ✅ 雙贏，可考慮採用 |
| 報酬↑ 但 MDD 變差 | ⚠️ 屬取捨，不算勝出 |
| 報酬↓ 但 MDD 改善 | ⚠️ 屬取捨，不算勝出 |
| 兩者皆劣 | ❌ 不採用 |

**單看報酬改善不算數** —— 這個系統的報酬與回撤本來就高度綁定（§4.5 #2），只看單一指標很容易被單邊改善騙。

### 4.2 即使勝出，也還不能上線

以下三點決定「這次結果能推論到什麼程度」，讀報告時務必一起看：

1. **樣本量極小**：4 個月、每組約 30 筆平倉交易。這種規模的單窗差異，噪音足以蓋過真實效果。勝出只代表「值得進一步驗證」，不代表可以換模型。
2. **`b2full` 混合了三個變因**（因子參數 + 特徵矩陣 + 訓練窗）。它贏了也無法歸因到其中任一項，要拆解得再跑「只換因子、不換訓練窗」的組合。
3. **要下結論必須多窗驗證**：至少 3~4 個不重疊子窗（如 2025H2、2026H1 各切幾段），看勝出是否穩定。判準沿用 §4.5 #4：**全窗雙贏 且 多數子窗穩健**，單窗改善易由少數期間驅動。

### 4.3 判讀陷阱：`b2full` 的因子可能根本沒變

`optimize_factors.py:453` 有**暖啟動**機制：會把上一輪 `best_factors.json` 的參數排入第一個 trial，讓 TPE 從已知好解展開。後果是 —— **若這次搜尋沒找到比現行更好的解，輸出的因子參數會與現行完全相同**，那 `b2full` 就退化成 `b2`，數小時等於白跑。

**看報告時先確認因子到底變了沒**：

```bash
python -c "import json; a=json.load(open('configs/best_factors.json',encoding='utf-8')); b=json.load(open('models/_candidate_b2full/best_factors.json',encoding='utf-8')); print('因子有變:', a['best_params_for_run_feature_engineering'] != b['best_params_for_run_feature_engineering'])"
```

報告的「重新搜尋出的技術指標參數」一節也會列出候選實際採用的參數，可直接與 §2 的現行值目視比對。

**這也是不建議用低 `--factor-trials` 的原因**：trials 太少時 Optuna 幾乎必然贏不過 seed，結果直接退回現行參數，得到的不是「快速看方向」而是「跟 `b2` 一樣的數字」。要跑就跑滿 `--full`（預設 600 trials）。

> 順帶一提：`b2full` 的截斷點（回測前一日）與現行因子的截斷點（`20250801`）不同，目標函式看到的資料範圍不一樣，所以在足夠 trials 下**有機會**找到不同的解 —— 但不保證。

### 4.4 反向結論同樣不成立

第一輪結果是三個候選中現行模型最好（見 §7），但這**不能推論成「舊模型比較好」或「模型永遠不用更新」**。三者 fit 終點 2023-11／2024-08／2025-12 與績效 +37.7／-11.8／+7.1 沒有單調關係 —— 沒有單調性正是「這更像噪音，而非資料新鮮度的系統性效應」的證據，兩個方向的強結論都需要多窗驗證才能下。

## 5. 怎麼跑

```bash
# 完整版：含貝葉斯因子調參，數小時等級，建議夜間執行
python scripts/compare_model_modes.py --full

# 降低 trials（不建議，見 §4.3：暖啟動會讓結果直接退回現行因子，等同白跑）
python scripts/compare_model_modes.py --full --factor-trials 200

# 只重訓模型的三方比較，數分鐘
python scripts/compare_model_modes.py

# 自選候選組合
python scripts/compare_model_modes.py --only b1 b2 b2full
```

其他參數：`-s/-e` 回測起訖（預設 2026-04-01 / 2026-07-31）、`-c` 初始資金（預設 200 萬，對齊既有月報表）、`-m` 最大持股檔數（預設讀 `config.MAX_POSITIONS`）。

### 耗時（2026-08-13 實測，2 trials 的微型跑）

| 步驟 | 實測 | 備註 |
| :--- | :--- | :--- |
| `optimize` | 3.7 分鐘 | 內含一次特徵重建（auto_pipeline 的設計：Optuna 需要基礎特徵）＋ 2 trials |
| `feature` | 1.8 分鐘 | 以新因子重建特徵矩陣（771,663 筆 / 110 特徵） |
| `train` | 0.4 分鐘 | 三個模型（Day1~3） |
| 每次回測 | ~0.5 分鐘 | 4 個月區間 |

**600 trials 的完整版推估約 1.5~4 小時**（`EARLY_STOPPING_ROUNDS=200` 可能提早收斂），主要成本全在 Optuna 搜尋。

**執行期間請勿同時執行 `Auto_RUN.py` / `run_daily.ps1`** —— 期間 `config.py`、`models/`、`configs/best_factors.json`、特徵檔都會被暫時替換。

### 產出

| 檔案 | 內容 |
| :--- | :--- |
| `reports/model_mode_compare_<TS>.md` | 比較報告（候選定義、績效表、增減判定、判讀注意事項） |
| `reports/compare_model_modes_<TS>.log` | 完整執行 log（自動落檔，不必自己重導向） |
| `reports/backtest_report_<起>_<迄>__<tag>.xlsx` | 各組交易明細 |
| `models/_candidate_<tag>/` | 候選訓練成果，**永久保留**；`b2full` 另含 `best_factors.json` 與特徵檔 |
| `models/_backup_incumbent_<TS>/` | 實驗前的現行狀態備份 |

## 6. 安全機制與出事處理

實驗結束（成功、失敗、Ctrl+C 皆然）會自動還原 `config.py` 四個變數、`models/`、因子檔與特徵檔。

**若行程被強制中止**（關機／當機／kill），`finally` 不會執行，環境會停在候選狀態。此時：

```bash
python scripts/compare_model_modes.py --restore-latest
```

會依 `models/_restore_manifest.json` 一次還原 config + 模型 + 因子檔 + 特徵檔。該 manifest 只在正常結束時刪除，所以**下次啟動若偵測到它殘留，程式會直接擋下並要求先還原** —— 這是防止在被污染的環境上跑出無效結果。

### 要採用某個候選

```bash
python scripts/compare_model_modes.py --promote b2full
```

- 會一併還原該候選的 `best_factors.json` 與特徵檔。**這點很重要**：`b2full` 的模型是用新因子參數算出的特徵訓練的，只換模型不換特徵會讓推論靜默失真。
- **不會改 `config.py`**。若要長期採用，需自行把該候選的 `BACKTEST_DATE` / `TRAIN_SPLIT_RATIO` / `VALID_SPLIT_RATIO` 寫回 `config.py`，否則下次 `auto_pipeline.py -s train` 會用舊設定重訓覆蓋掉。

## 7. 第一輪結果（2026-08-13，只重訓模型，未含因子調參）

回測 2026-04-01~07-31、200 萬、5 檔，風控參數為當時 `config.py` 現值：

| 指標 | `incumbent` | `b1` | `b2` |
| :--- | :--- | :--- | :--- |
| 實際 fit 訓練集終點 | 2023-11 | 2024-08 | **2025-12** |
| 區間報酬 (%) | **+37.68** | -11.80 | +7.07 |
| 最大回撤 (%) | **-15.75** | -25.20 | -24.08 |
| Calmar | **2.39** | -0.47 | 0.29 |
| 賣出勝率 (%) | 33 | **37** | 29 |
| 平均每筆損益 (%) | **+9.43** | -1.76 | +4.79 |

**結論**：兩個候選對現行都是報酬、回撤雙輸 → 不採用，維持現行模型。「模型訓練資料不夠新」不足以解釋近月績效。

順帶再次印證 §4.5 #1：`b1` 賣出勝率最高（37%）卻報酬最差 —— 進場命中率與獲利無關。

**範圍限制**：這一輪只重跑 `train.py`，`best_factors.json`（2026-06-21、截斷 20250801、600 trials）與 `best_trading_params.json` 固定、特徵檔三組共用。**「完整重跑 optimize→feature→train 是否有用」由 `--full` 那輪回答，尚未執行。**

## 8. 程式驗證紀錄（2026-08-13）

`--full` 完整流程已用 2 trials 微型跑驗證過，全段通過：`optimize` → `feature` → `train` → 回測 → 自動還原（`config.py` 四個變數、`models/`、`best_factors.json`、特徵檔皆比對 hash 確認復原）。

過程中出現一個值得記錄的**一致性驗證**：該次 `b2full` 因暖啟動（§4.3）退回現行因子參數，於是

- 重算後的特徵檔與現行 **byte-identical**
- 產生的模型與 `b2` 候選 **byte-identical**
- 回測結果與 `b2` 完全相同（+7.07% / -24.08% / 31 筆）

代表整條 `optimize→feature→train` 管線在「因子未變」時會精確退化成 `b2`，沒有引入任何意外變異，特徵重算也是決定性的。**若正式跑完後發現 `b2full` 的數字與 `b2` 一模一樣，先別懷疑程式，去檢查 §4.3 的因子是否真的變了。**
